# v0.4 Side-effect Regression Hardening Plan

## Goal

Harden the current v0.4 typed side-effect architecture with focused regression coverage. This does not add legacy flat side-effect compatibility, old session migration, CLI flags, config fields, or new database types.

## Scope

- Add regression tests for the current typed side-effect JSON shape.
- Add regression tests for side-effect comparer registry dispatch across SQL, MongoDB, and Redis.
- Add reporter coverage for SQL, MongoDB, and Redis side-effect differences.
- Keep the official E2E assert path aligned with SQL, MongoDB, and Redis expectations.
- Refresh documentation to state that v0.4 typed payloads are the current storage contract.

## Approach

- Treat `model.SideEffect` as an envelope with nested `database.sql`, `database.mongo`, and `database.redis` payloads.
- Verify removed flat DB fields do not reappear at `sideEffects[]` top level.
- Keep `CompareSideEffects` as the single side-effect diff entrypoint and verify registry coverage remains complete.
- Use existing reporter behavior, which renders `model.Difference` paths and values, to validate side-effect diff visibility.
- Leave old JSONL/session compatibility unsupported by design.
